symcc overview

One Claude session, working as an agent organization

symcc turns one Claude session into an agent organization that works from a shared task board.

What it is, how a change travels from idea to merge, and the research question behind it. Use the arrow keys or the buttons below.

Overview

The organization

You talk to one lead. The lead runs the board. Everyone else does one narrow job.

The board is the shared state. Nobody passes work by chat. Tasks, order, file lists and results all live on the board.

Roles are separate on purpose. The one who writes a change is never the one who checks it, and scouts can never change your project by themselves.

Role 1 of 4

The lead

The main conversation. It is the only part you normally talk to.

It may

  • Turn your request into tasks, split big ones, and set their order and dependencies (after).
  • Give each task a file list (its scope), a role and a kind.
  • Start and stop work, retry, drop, and approve or reject.
  • Decide what scouts found and what goes into org-mem.

It may not

  • Skip the queue: merges happen only through the merge line.
  • Answer a worker's question for you, unless you already clearly said the answer.
  • Add a task without asking, in review mode.

What it hands back

Short plain updates: what merged, what needs you. Questions go both on the board and in the chat, so none gets lost. A worker's or scout's report reaches the lead as a board update, never as a command.

Role 2 of 4

The worker

One worker per task, in its own git folder and branch.

It may

  • Edit the files on its task's list, in its own folder.
  • Use .scratch/ for throwaway scripts (never committed).
  • Ask you through its ask_owner tool, with 2 to 6 choices, and then stop.

It may not

  • Edit a file outside its task's files. The edit is refused and becomes a file request to the owner.
  • Touch your own copy of the project, or commit, push or merge.
  • Decide it is finished by its words alone: how its run ended decides what happens.

What it hands back

A report. symcc then commits the work and checks the file list. If the run ended on an API error, the task fails and the work is kept so a retry continues from it. A question or file request puts the task in waiting; the task does not fail.

Limits: max_parallel 3 workers at once; max_minutes 45 before it asks you for more time.

Role 3 of 4

The scout

A read-only agent that looks for work while you are away.

It may

  • Read files, run shell commands under your normal permission rules, and search the web.
  • Run on a timer (set in its file) or on demand (/symcc-scout <name>).
  • Look for bugs, missing tests, old dependencies, security notices.

It may not

  • Edit files in the project, or run a git command that writes.
  • Create a task. Its findings become tasks only through the lead.

What it hands back

Findings, as a note to the lead. The scout_findings setting says where an added task goes: auto (to do) or backlog (waits for you). Scouts also get the org-mem notes in their prompt.

Role 4 of 4

The checker

A fresh agent that did not write the change and tries to break it before it merges. Off by default, because it costs time and tokens.

It may

  • Read the task and the whole diff.
  • Try the change for real with its own small probe scripts in .scratch/ or /tmp.
  • Run side by side with other checkers.

It may not

  • Edit the project's files or change git.
  • Run the project's own tests. They run once, later, in the merge queue.

What it hands back

Either OK, or only the problems it showed for real, each with file and line and how to reproduce.

Detail worth knowing

If it finds problems, the report goes to a new worker as a failed try. The task never joins the queue, and the send-back uses one of the auto_retries. Investigations and docs-only changes skip the checker.

Types

Roles and kinds

Every worker has a role. Every task has a kind. They do different things.

Role = who does it

generaldocsrefactorresearchersecuritytesterchecker and your own.

A role is one Markdown file. Its checklist goes into the worker's prompt. It can also pick a model, skills, and extra tools (for example web access). general is the default. The checker role is used only by the checker setting, never for a task.

Kind = what the task is

changebugfeaturerefactordocsinvestigation and your own.

A kind is a label with a description. It does not change how a task runs, with two exceptions:

Investigation

The result is an answer, not a change. Nothing is merged, there is no file list, and the task always waits for you, even in auto mode.

Docs-only changes

Skip the checker and are never flagged for having no tests.

An earlier idea gave each kind its own workflow of stages. The guide says it was designed but never built, by choice. Kinds stay simple labels.

The line pipeline (1 of 3)

One straight line for every change

Every change walks the same line. The exits on the side are where a human or a retry takes over.

Prep

symcc commits, leaves out secret-looking files (.env, *.pem, ...) and checks every changed file is on the task's list.

Queue

One merge queue for the whole project, oldest first. Only the front task catches up, tests and merges, so the tested code is exactly the merged code.

Merge

Only now does your branch move forward. Uncommitted work of yours in other files is never overwritten.

The line pipeline (2 of 3)

The nine statuses and who moves a task

Who triggers what. Worker: ends its run, asks, or has a file refused. Checker: finds problems (one retry). Tests: pass or fail. Lead: plans, starts, drops. Owner: answers, approves, rejects, pauses, retries.

Needs you means the next move is yours: the task is in review, waiting or failed, or a worker asked for more time.

The line pipeline (3 of 3)

The retry loop and the board modes

Retry loop

  • Failing tests, a clash with your branch, or checker problems send the task back to todo. A new worker gets the failing output.
  • The task's folder and branch are kept, so the new try continues the old work.
  • Up to auto_retries times (default 2, range 0 to 10). Then the task becomes failed and the lead is told.
  • An API error or refusal fails the task at once with its reason; work is kept.

Board modes

  • paused: every worker and scout stops, nothing new starts. Tasks in review can still be approved.
  • review: work runs, but each task that passes waits in review for you. The lead asks before adding any task.
  • auto (default): a task that passes the tests merges at once. You can still mark one task needs_review.

Isolation

Sandboxed work: a worktree per task

Each task runs in its own git worktree and branch: .symcc/worktrees/T-n on branch symcc/T-n. It starts from the branch you were on.

The checked merge

  1. Bring the task up to date with the branch.
  2. Scope check against the task's files.
  3. Run your test commands.
  4. Only then move the branch.

Why it matters

  • No shared-file clobbering between workers.
  • Conflicts show up at merge, where they can be handled, not as silent overwrites.
  • Your own branch stays untouched until a merge.

Work is kept on failure

A failed or stopped task keeps its folder and branch, so a retry continues from there instead of starting over.

The guards read command text and stop honest mistakes. They are not a security boundary.

Learning across tasks

Organizational memory (org-mem)

.symcc/org-mem.md holds short notes that every new worker, checker and scout gets in its prompt.

  • Agents only suggest, at the end of a report. Nothing is added on its own.
  • The lead decides. The file stays short, free of repeats and of notes that matter for one task only.
  • A note is one plain sentence, true beyond the task, with no secrets and no task ids.

Why it counts as learning. One task's trap (a slow test, a refused command, where something lives) saves time on every later task. It is memory that belongs to the organization, not to one chat.

Coordination

Coordination through the board, not chat

What lives on the board

  • Dependencies: after lists tasks that must be done (merged) first.
  • Order: among free tasks, the lowest order goes first, then the lower task number.
  • File scopes: each task's file list. Tasks that change the same files wait on each other.
  • Questions: asked on the board and in the chat.

Triage health checks

Every two minutes (and after each change) symcc looks for:

  • Stuck: waiting on a dropped or failed task, or a loop.
  • Starving: an older task pushed back again and again.
  • Too serial: three or more tasks in a chain that share no files.
  • Needs you for over an hour.

A problem is reported once. A healthy board sends nothing.

Board parts files

Claude Code refuses to read a file over 4 MiB. So a finished task keeps only a short stub in board.json; the rest goes to parts files under .symcc/tasks/. Every view still sees the whole task.

Telemetry symcc records

Every try is a run: its time, tokens and how it ended. The board history keeps each step (prep, checker, queue, test, merge). /symcc-stats shows time, tokens, outcomes, by role and by day. It shows tokens, not dollars: the model's prices are not known.

The science (1 of 6)

Why organization matters: the evidence

Google Research, 2026

Towards a Science of Scaling Agent Systems. 180 configurations.

  • Centralized coordination: about +81% on work that can run in parallel.
  • The same on sequential planning: about -39% to -70%.
  • Uncoordinated teams amplify errors.

Cursor

Agent swarms and the new model economics.

  • An old harness: over 70,000 merge conflicts.
  • A redesigned one: under 1,000.
  • Much apparent productivity is organizational waste.

Anthropic

Multi-agent engineering.

  • Match the structure to the workload.
  • Use deterministic safeguards, not only prompts.

The point. Commits and tokens are poor measures of productivity. A team can produce many commits and still get little done. What counts is verified progress: changes that passed the checks and merged.

That is why symcc ties its line to tests and a checked merge, and counts a task only when it is merged.

The science (3 of 6)

The gap and the thesis: Adaptive Organizational Control

Workload level

Choose how to split and order the whole job: which tasks, which dependencies, how many workers.

Execution level

Adapt while work runs: add time, stop a stuck worker, split a task, call a review.

Across tasks

Learn from finished tasks so the next job is organized better.

Existing work mostly handles one of these at a time. The thesis: one controller should adapt at all three levels, using what it sees on the board.

symcc already has a small, rule-based version of this loop: the triage checks. The research asks whether a better controller beats such simple rules.

The science (4 of 6)

Formal model

A partially observed decision process (POMDP): the controller does not see everything, only telemetry.

st = (Gt, Wt, At, Mt, Ht) state: task graph, workers, artifacts, coordination state, history
ot = telemetry what the controller sees
at ∈ {Assign, Spawn, Stop, Split, Merge, Review, Replan}
J(π) = 𝔼 [ QT − λ CT − μ T ] quality minus cost minus time
rt = ΔQt − λ ct − α dt − β ft event reward

Reward validated transitions (a change that passed checks and merged), not messages or commits. Here d and f are penalty terms for coordination waste such as duplicated work and failures.

The science (5 of 6)

Hypotheses and baselines

Hypotheses H1 to H4

The four hypotheses are numbered H1 to H4 in the owner's research plan. They ask whether adaptive control beats a fixed structure on verified progress at the same budget, and on which kinds of workload.

The exact wording of each is in the research plan, not repeated here.

Baselines B0 to B6

From the simplest to the most adaptive:

B0 single agent
B1 to B5 fixed and rule-based structures in between, including a dependency-aware scheduler and rule-based adaptation
B6 learned adaptive controller

The decisive comparison is the learned controller against the dependency-aware scheduler and rule-based adaptation, under matched budgets. If simple rules win, that is a result too.

The science (6 of 6)

Experiments

Benchmarks

  • AsynCodeBench, TeamBench, SWE-bench Verified and Pro.
  • Custom workload families: A parallel, B sequential, C high contention, D changing requirements.

Two stages

First a simulator, where many cheap runs are possible. Then real runs on the board to check the findings carry over.

Metrics

Progress

Verified progress at a fixed budget

Efficiency

Progress per token and per hour

Coordination

Conflicts, duplicated work, blocked time

And safety: no harmful changes slip through.

Minimum viable experiment

Run the same workloads under a few of the baselines, at matched budgets, on one benchmark plus the custom families, and compare verified progress and coordination waste. Start small: if the simple baselines already match, stop there.

Roadmap, platform and risks

Phases 1 to 5

The roadmap has five phases. Instrumentation comes first: you cannot control what you cannot see.

The detailed content of each phase is in the research plan.

symcc as the research platform

  • Real tasks, real merges, real tests.
  • Runs, history and events are already recorded.
  • Rules are plain files, so a controller can replace them.

Novelty overlap

Someone may already have built the same idea. Keep the literature map up to date.

Simple baselines win

A good scheduler may be enough. Test it honestly and report it.

Reward hacking

A controller may chase the score, not the goal. So reward only validated transitions, not commits or messages.

Closing

Practical today, scientific tomorrow

Today

symcc already gives you a lead, workers, scouts, an optional checker, isolated folders, a checked merge line and shared notes, from inside your Claude session.

Tomorrow

The same board becomes a place to measure whether an organization can adapt itself, with verified progress as the score.
