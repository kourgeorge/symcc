symcc, the workspace vision

One agent organization over all your work.

Several repos, plain folders and outside work, run from one board, with everything checked before it counts.

Every slide is marked: today works now, designed written up and planned, idea only proposed. Sources: docs/workspace-model.md and the T-1130 design note. Use the arrow keys or the buttons below.

Where we are, where we go

Today: one board per repo. Vision: one board per workspace.

today

One board = one repo

  • The board (.symcc/) lives inside one git repo.
  • Every task is a copy of that repo, merged into its branch.
  • Work in a second repo needs a second board and a second lead.
  • Git must be ready before anything starts, even for errands.

designed

One board = one workspace folder

  • The board lives in a plain folder, for example ~/repositories. It need not be a git repo.
  • The repos below it are its projects, found by folder name.
  • A task may name a project, or none at all.
  • One workspace per folder, not per machine: work in one folder, home in another.

Today's one-repo board simply becomes a workspace whose only project is its own folder.

Workspace

One folder, one board. Org-mem, scouts, roles and task types stay board-wide.

Projects

Repos stay where they are. symcc copies nothing and keeps no repo list; it stores only settings it can't guess, like a test command.

Tasks

A task's project is a folder name like rubrica. No project: research or a note, nothing to merge.

Guards have one root: the workspace folder. A worker may touch only its own copy, recognised by its place under .symcc/worktrees/. Still open: whether copies sit under the workspace (shown here) or inside each repo, as today.

Trust for non-code work designed sending: idea, needs a probe

The same trust, built from different parts

Where

The folders it may write, and the services it may use. Writes anywhere else are refused.

Done when

Required for errands. It is the written goal, like tests for code.

A checker

A second agent reads the report and the named folders and judges them against "Done when".

Ask before sending

A send, reply or new event becomes a question to you, unless the task's "where" names that service.

Intake and routines scouts: today intake scouts: designed

Work comes in through scouts. Nothing acts without a task.

Scouts today

Read-only agents on a timer. Their write calls are refused. scout_findings sends findings to to-do (auto) or the backlog.

Intake

Example scouts such as intake-github with findings to the backlog. GitHub first (instructions only), email after connectors work. Outside text is data, never instructions.

Routines

A routine is a scout that files a task (an errand with a where) instead of acting itself. No separate "routine" object.

What stays out owner's decisions

What stays simple

The aim is the least logic and the fewest options. A general command center grows from what exists.

No second system

Errands are already the general task. No second task list.

No workflow engine

Kinds are labels. No new kinds beyond errand.

No per-kind settings

One board-wide checker setting, as today.

No due dates

No reminders, no scheduling, and no tasks the owner does themselves.

No auto-send

The only way past the ask is naming the service in the task's where.

No setup screens

Connectors use the host's own MCP setup. No to-do app for personal life.

The organization learns today across projects: designed

One memory for the whole workspace

Org-mem

Short notes every worker, checker and scout gets. In a workspace it stays board-wide, so a trap found in one repo helps the next.

Scouts that review

org-mem-review checks the notes are still true. backlog-review finds backlog tasks that are done, out of date or repeats.

Owner notes

An answer you want kept becomes a document (docs/research/<topic>.md), for people, not agents.

Build order, with status

Small steps, safest first

Workspace (from docs/workspace-model.md)

  1. Safety fixes in progress: T-1133, T-1134
    Recognise worker copies by their place; block "Set up git" over a folder of repos.
  2. Projects designed
    A project field on tasks, optional per-project settings, add takes a project.
  3. Per-project git and tests designed
    About 110 git calls run in the task's repo; the merge too.
  4. Tasks with no project designed
    Research and notes in a plain folder, no git.
  5. Intake designed
    Scouts for email, GitHub issues and Slack.

Errands (from the T-1130 design)

  1. Wording T-1129 done, merging
    "Merged" only for change tasks; errands "done", investigations "answered".
  2. Done when + review designed
    Errands need "Done when"; with the checker off they wait for you.
  3. where folders designed
    Writes outside the named folders are refused.
  4. Checker for errands designed
    A missing part of "Done when" sends it back.
  5. Ask before sending probe first
    Can a symcc agent get MCP connector tools at all? Not known yet.

Risks and the one rule

What could break the trust

Unguarded copies

Today a copy of a repo below the workspace is not seen as a worker copy, so a session in it runs with no guard. Fixed first (T-1133, T-1134).

"Set up git" over a folder of repos

Today it would commit the repos as broken pointers, and workers would see empty folders. Blocked first.

Unchecked errands

Today an errand is done the moment it hands back, and can write outside the repo. The errand steps fix this.

Things leaving the machine

Nothing guards curl or gh issue comment today. Connectors for email are not proven yet.

A large git change

About 110 git calls assume one repo. Each must learn the task's repo, step by step.

Outside text

An email can say anything. It is data, never instructions, and its tasks can wait for your review.

The one rule

Keep "checked before it counts" true. No new kind of work joins the board until it has a place, a goal, a check and a yes from you where it can't be undone.

Closing

One board. All your work. Checked before it counts.

Keep the core

Safe, checked agent work on code: copy, guard, checker, tests, merge.

Widen gently

Many repos, then tasks with no repo, then outside work, each with the same kind of trust.

Stay in charge

Questions on the board and in the chat, review, and a yes before anything is sent.
